# Архитектура «Бережно» — мягкая подготовка к беременности

Версия документа 1.0 · соответствует ТЗ v1.0

## 1. Стек и почему он такой

| Слой | Выбор | Почему |
|---|---|---|
| Интерфейс | React 19 + TypeScript | как в ТЗ |
| Стили | Tailwind CSS 4 (компиляция через API) + токены палитры | как в ТЗ |
| Сборка | esbuild (вместо Next.js) | приложение публикуется на GitHub Pages — это статический хостинг без сервера. Серверные возможности Next.js там недоступны, а статический экспорт Next.js сложнее и тяжелее. esbuild даёт один маленький JS-файл, плоскую структуру и мгновенную сборку |
| Серверная логика | Supabase: PostgreSQL + Auth + RLS + RPC-функции | роль «защищённых API» выполняют функции `push_changes`, `pull_changes`, `delete_my_data`, `delete_my_account` в базе; доступ к строкам ограничен Row Level Security |
| Клиент Supabase | собственный минимальный клиент (fetch к `/auth/v1` и `/rest/v1/rpc`) | нет лишних зависимостей, весь код проверяем; публичный `anon`-ключ безопасен при включённом RLS, секретный `service_role` в клиенте не используется |
| Локальное хранилище | IndexedDB (своя обёртка) + кеш в памяти | офлайн-работа и офлайн-очередь; данные не в localStorage |
| PWA | manifest + свой service worker | установка на экран «Домой», работа без сети, баннер обновления |
| Графики | свои SVG-компоненты | лёгкие, адаптивные, с подписями (цвет не единственный носитель смысла) |
| Тесты | node:test (unit), PostgreSQL 16 (SQL + RLS), Playwright (e2e) | см. `docs/TEST_REPORT.md` |

## 2. Схема экранов

```
Мобильный (нижняя панель)          Десктоп (боковое меню)
┌──────────────────────────┐       ┌────────────┬──────────────────────────┐
│ Шапка: дата, статус синх.│       │ Главная    │                          │
│                          │       │ Питание    │   Контент (до 960 px,    │
│      Контент экрана      │       │ Привычки   │   на главной — 2 колонки)│
│                          │       │ Движение   │                          │
│                          │       │ Цикл       │                          │
├──────────────────────────┤       │ Календарь  │                          │
│ Главная Питание Движение │       │ Знания     │                          │
│ Цикл  Ещё                │       │ Статистика │                          │
└──────────────────────────┘       │ Настройки  │                          │
                                   └────────────┴──────────────────────────┘
```

- **Главная** `#/` — приветствие, дата, кольцо выполнения, контексты дня («У меня мало сил», «Я в разъездах» и др.), план дня с действиями (Выполнено · Короткая версия · Перенести · Пропустить сегодня · Изменить расписание · Скрыть), назначения, вода, фрукты и овощи, ближайший приём пищи, разминки, йога, события цикла, неделя.
- **Питание** `#/food` — вкладки: Меню (7/14 дней) · Рецепты (любимые и новые) · Покупки (+ запасы) · Перекусить · Анализ.
- **Привычки** `#/habits` — список, редактор (полная/минимальная версия, расписание, пауза, удаление), идеи новых привычек.
- **Движение** `#/move` — Йога (расписание 2×/нед, каталог, плеер с таймером, видео) · Разминки (шея и плечи, спина, запястья, глаза, общая, ходьба) · Рабочий график · Активность (ручной ввод, Apple Health — статус).
- **Цикл** `#/cycle` — прогноз и неопределённость, отметка менструации, симптомы, тесты на овуляцию (модуль скрываемый), история циклов, режим беременности.
- **Назначения** `#/meds` — «Мои назначения»: средства, дозировки (вводит пользователь), отметки, история, проверка дублирования компонентов.
- **Календарь** `#/calendar` — день/неделя/месяц, фильтр категорий, заметки дня.
- **Знания** `#/library` — проверенные материалы с уровнем доказательности, источником и датой проверки.
- **Статистика** `#/stats` — привычки, питание, активность, цикл; **Годовой план** `#/year`.
- **Настройки** `#/settings` — профиль, цель, модули, облако и вход, статус синхронизации и конфликты, напоминания `#/reminders`, экспорт/импорт, удаление, конфиденциальность, ограничения.

## 3. Модель данных

Все таблицы в Supabase устроены одинаково («конверт» + документ):

| Поле | Тип | Назначение |
|---|---|---|
| `user_id` | uuid → auth.users, каскадное удаление | владелец; RLS `user_id = auth.uid()` |
| `id` | text | идентификатор записи; первичный ключ `(user_id, id)` |
| `data` | jsonb | содержимое записи |
| `created_at` | timestamptz | создание |
| `updated_at` | timestamptz | момент изменения на устройстве — для разрешения конфликтов |
| `deleted_at` | timestamptz | мягкое удаление (надгробие), чтобы удаление дошло до всех устройств |
| `server_updated_at` | timestamptz | ставит сервер; курсор синхронизации |
| `rev` | int | номер ревизии на сервере |
| `device_id` | text | какое устройство последним меняло запись |

Индексы: `(user_id, server_updated_at)` во всех таблицах; `(user_id, (data->>'date'))` в журналах по дням. История изменений важных сущностей (назначения, рецепты, цикл, тесты, привычки, настройки) пишется триггером в `record_history`.

Детерминированные идентификаторы (`prefs`, `hl:<привычка>:<дата>`, `day:<дата>`) делают так, что одна и та же отметка, сделанная офлайн на двух устройствах, сливается в одну запись, а не дублируется.

## 4. Синхронизация

1. Каждое изменение сразу пишется в IndexedDB с флагом «не отправлено» (офлайн-очередь переживает перезагрузку и закрытие).
2. Через ~1,5 с после изменения, при возврате в приложение, при появлении сети и раз в минуту клиент вызывает `push_changes(rows)` — одна транзакция на пакет. Сервер принимает запись, только если её `updated_at` не старше сохранённой.
3. Затем `pull_changes(since)` — одна выборка изменений всех таблиц после курсора (с перекрытием 10 с на случай параллельных транзакций).
4. Конфликт (на сервере более новая версия записи, которую мы меняли офлайн): побеждает более позднее изменение, проигравшая версия не теряется — она сохраняется в журнал конфликтов и её можно восстановить в Настройках.
5. Статус синхронизации всегда виден в шапке: «Сохранено на устройстве», «Синхронизация…», «Всё синхронизировано», «Нет сети — изменения отправятся позже», «Ошибка».

## 5. Технические риски и ограничения

| Риск | Решение |
|---|---|
| Push-уведомления на iPhone работают только у приложения на экране «Домой» (iOS 16.4+) и требуют сервера отправки | В MVP: напоминания внутри открытого приложения + выгрузка в системный Календарь (.ics) с сигналами — работает в фоне на iPhone, Mac и Windows. Настоящий Web Push — следующий этап (Supabase Edge Function + pg_cron + VAPID) |
| Веб-страница не имеет доступа к HealthKit | Ручной ввод шагов и тренировок. Интеграция — только отдельным iOS-приложением (Swift, HealthKit, учётная запись Apple Developer $99/год). Не имитируем |
| Нет открытого API ВкусВилл и Азбуки вкуса | Каталог перекусов — идеи без выдуманных цен и остатков; свои товары пользователь добавляет вручную (название, состав, цена, ссылка — только если указаны) |
| У приложения на экране «Домой» отдельное хранилище от Safari | Онбординг предлагает сначала войти в облако; подсказка в Настройках |
| Сброс хранилища браузером | `navigator.storage.persist()`, облако, экспорт в файл |
| Неточность календарного прогноза | Показываем диапазоны и пояснение, что прогноз не подтверждает овуляцию |
| Медицинские данные | Не даём доз и диагнозов; справочник — только проверенные источники с датой проверки |
| Часы устройств расходятся | Порядок синхронизации задаёт сервер (`server_updated_at`), конфликты сохраняются |
